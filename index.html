Personal project · Jun–Sep 2026

Inference Server

Blip becomes a request.

An async image-classification server with a Redis queue and batched workers.

A small model-serving system I built from scratch to learn what happens between an HTTP request and a prediction. A FastAPI server accepts each image and hands it to separate worker processes through Redis. The workers group waiting images into batches, run each batch through ResNet-18 in one pass, and send every answer back to the exact request that is waiting for it. I also wrote the load tester that drives it with up to 1,200 concurrent requests.

  1. An image comes in.

    POST / · multipart upload · FastAPI on Uvicorn

  2. It gets a 16-byte ticket and parks on an asyncio Future. The event loop keeps serving other requests.

    job_id = uuid4().bytes · pending_jobs[job_id] = Future()

  3. The image waits in Redis under its ticket. Only the 16-byte id joins the line.

    SET job_id <image bytes> · RPUSH jobs job_id

  4. Worker processes (four in my tests) pull from one FIFO list. The first idle worker opens a batch.

    BLPOP jobs 1 · torch.set_num_threads(1)

  5. The batch closes at 8 jobs or after 200 ms, whichever comes first.

    BLPOP jobs 0.05 · BATCH_SIZE = 8 · BATCH_FILL_WAIT_TIME = 0.2

  6. One round trip fetches every image, and one more deletes them.

    MGET id1 … id8 · DEL id1 … id8

  7. One ResNet-18 forward pass labels the whole batch.

    torch.stack → [8,3,224,224] → no_grad → [8,1000] → argmax

  8. Each answer goes home as 24 bytes, and one reader task wakes exactly the right request.

    struct.pack('<16sq') · RPUSH response · BLPOP response 1 · set_result

What I built

  • Split serving into one async FastAPI frontend and separate worker processes that talk only through Redis, so inference never runs on the web event loop.
  • Matched responses to requests without polling: each request awaits a Future keyed by its 16-byte id, and one background reader completes the right one.
  • Replies are a fixed 24-byte binary message, struct '<16sq' (UUID plus int64 class index), not JSON.
  • Dynamic batching: up to 8 jobs or 200 ms, one MGET, one DEL, and one stacked forward pass on CPU under torch.no_grad.
  • Found why the reader task died silently: redis-py 8's 5 s default socket timeout killed an unbounded BLPOP after 5 s of idle. Fixed it with a bounded 1 s BLPOP and a done-callback that prints the task's exception.
  • Wrote an asyncio + httpx load generator (10 to 1,200 concurrent requests per level, p25 to p95 latency, failures grouped by status code). I raised its read timeout to 30 s after noticing the 5 s default was dropping slow requests from the stats.
  • Capped each worker at one PyTorch thread so workers don't fight over cores, and gave the reader its own Redis connection.

What I'd fix next

  • Give the Future a timeout. An image that fails to decode currently leaves its request waiting forever.
  • Put a TTL on payload keys.
  • Give each frontend its own response list. One shared list means one frontend process.
  • Find the cause of the 502s that show up from 700 concurrent requests up.

No speedup number yet. The same unbatched code measured about 2× apart on two different days, so batching gets a controlled, interleaved rerun before it gets a number.

Research · SOCR lab, University of Michigan · 2026

SOCR BrainGen

Blip becomes noise.

Synthetic brain MRI with tumors placed by lobe, about 10 seconds per image.

In the University of Michigan SOCR lab I built an atlas-guided diffusion model that generates synthetic brain MRI slices. You choose where a tumor appears (which lobe, how high in the brain, how large), and about 10 seconds later you get a synthetic FLAIR image with a lesion there. I trained it on the public BraTS 2023 dataset on the university's Great Lakes cluster, added it as a sixth model to the lab's web app on a feature branch (not merged yet), and deployed its backend on Hugging Face ZeroGPU. I also built the harness that scores the lab's generator models.

The lab's web app and its GAN models came before me; they're my labmates' work. Mine are the conditional diffusion model, its GPU backend, and the evaluation harness. Advisors: Profs. Ivo Dinov and Simeone Marino. A manuscript is in preparation.

  1. Pick a lobe and a tumor size. The real panel greys out the 7 of 18 lobe-and-height combinations the data can't support.

    Tumor · Lobe (6) · Slice level (3) · Size (3)

  2. One random seed drives both the tumor shape and the starting noise, so any image can be regenerated.

    seed → NumPy (mask) + PyTorch (noise)

  3. Anatomy comes from a held-out real scan in a conditioning bank, plus six lobe probability maps from an atlas.

    T1 from a 42-slice bank · ICBM452 lobe maps

  4. The tumor is drawn first, inside the chosen lobe. It's an input to the model, not a prediction.

    synth_mask: atlas × compactness × smoothed noise · core = 30% of lesion

  5. Generation starts from pure static.

    x ~ N(0, I) · 1×1×256×256 · cond 1×8×256×256

  6. Then 200 steps: the U-Net predicts the noise, and the DDIM scheduler removes a calibrated share of it.

    t = 995, 990, …, 5, 0 · 85,261,185-parameter U-Net

  7. About 10 seconds from click to image on Hugging Face ZeroGPU, about 6.3 s of it on the GPU.

    [-1, 1] → [0, 1] · FLAIR + Tumor Mask PNGs

What I built

  • Added a sixth model, an atlas-guided conditional diffusion model, to the lab's brain-MRI web app on a feature branch. It took about 8.2k lines across backend inference, API endpoints and UI. The controls grey out the 7 of 18 lobe-by-level combinations the data can't support, so the site never quietly swaps in a different request.
  • Deployed the backend as one Hugging Face ZeroGPU Gradio Space. The five GANs run on CPU and use no GPU quota; only the diffusion loop goes to the GPU, through a single function rebinding.
  • The 85,261,185-parameter U-Net loads with strict=True plus a parameter-count check. A non-strict load can silently turn a mismatched checkpoint into random weights that still look brain-shaped.
  • Wrote an atlas-conforming tumor generator. It seeds the lesion inside the chosen lobe and sizes it to that lobe's area (small 5–12%, moderate 15–35%, large 40–60%), split into edema and an enhancing core. The code is one file kept byte-identical in the research and web repos, and it matched the original SciPy version on all 78 test cases (Dice 1.0).
  • Built the research pipeline: registered the ICBM452 lobe atlas into BraTS space with ANTs SyN, preprocessed about 1,250 BraTS 2023 patients into 163,974 nine-channel slices, and trained on U-M's Great Lakes GPUs with mixed precision and EMA weights.
  • Built an evaluation harness for all 8 lab generator checkpoints: strict loading, a common 128×128 grid, no-reference metrics with 1,000-resample bootstrap confidence intervals, and a model-to-model FID matrix. I audited it against 27 candidate measurement defects and fixed the five that were real.
  • Caught shipping bugs on the first real GPU run: an 8-vs-9-channel mismatch, a csv-vs-json manifest name, and a safetensors version conflict that would have broken every redeploy.

I also explored CLIP text conditioning through cross-attention and a 3D (64³) diffusion pipeline. Both are experiments, not finished features.

About the drawing: the slice is procedural and the noise schedule is illustrative. It is not model output and not patient data. With η = 0 and a perfect noise estimate, DDIM's path is exactly x_t = √ᾱ_t·x₀ + √(1−ᾱ_t)·ε, which is what the figure draws. Status: integrated on a feature branch of the lab's repo, not merged into the lab's live site yet.

A live spacesuit telemetry screen and an onboarding simulator for a NASA SUITS team.

Teammates built the Flask/Socket.IO backend, the Unity headset client, and the map and rover pages. The EVA screen, its alert rules, and the onboarding simulator are mine.

  1. NASA's Telemetry Stream Server answers an 8-byte question.

    UDP · [uint32 timestamp][uint32 command = 1 (EVA)] → JSON

  2. The team's backend broadcasts each feed to every screen, about every 6 seconds.

    socketio.emit('eva-telemetry') → React + Unity

  3. My EVA page checks 22 suit readings for each of two astronauts on every update.

    checkRanges() · 22 ranges · 10 rate limits

  4. Out of range is danger. Off nominal is a warning. Changing too fast gets flagged.

    < min or > max → danger · ≠ nominal → warn · |Δ|/Δt > limit → fast

  5. Alerts are deduped by id, sorted danger-first, and tint the matching gauges.

    dedupe by id · danger first · newest 5

  6. For new teammates, I built a fake NASA that runs on a laptop at 5 Hz.

    mock_tss.py · FastAPI /ws · panel.py · TssClient.cs · pytest

Solo project · Windows service · Feb–Mar 2026

Noverwatch

Blip tries to play Overwatch.

A Windows service that kills Overwatch the moment it launches.

I wrote a small Windows service to keep myself off Overwatch. It runs quietly in the background, and the moment Windows reports that Overwatch has started, it writes the attempt to a log and shuts the game down. It works: its log shows 8 kills, all during testing in March 2026.

The game launches. Then it doesn't.

  1. I wrote a Windows service to keep me off Overwatch.

    .NET 10 worker service · runs as LocalSystem

  2. I press Play. Windows creates the game's process first; nothing stops the launch itself.

    Overwatch.exe · PID 12400 (example)

  3. Windows announces every new process. The service is subscribed to those announcements, so it isn't polling.

    SELECT * FROM Win32_ProcessStartTrace · name == config["Games"]

  4. It logs the attempt, then kills the process.

    append log.txt · Process.Kill() · LogCritical

  5. Then it goes back to listening.

    heartbeat: "The Noverwatch system is online" every 100 s

How it works

  • Event-driven: it subscribes to Windows process-start events through WMI instead of scanning the process list.
  • The target game is read from appsettings.json, not hard-coded.
  • On a match it appends the name, PID and time to a log file, ends that process (only the matching PID) with Process.Kill(), and logs at Critical level.
  • It runs as an installed Windows service (LocalSystem, manual start). The hosting follows Microsoft's BackgroundService tutorial; the detector is mine.
  • It ships as one self-contained, single-file exe of about 89.5 MB that needs no .NET install. That's 89.5 MB to close one game.
  • 42 publish attempts, 14 of them failed. Then it worked.

What I'd fix next

  • Every 100 s heartbeat creates a new watcher without disposing the old one.
  • Detection only starts if Information-level logging is on, so raising the log level would silently switch it off.
  • "Blocked n" counts per watcher, not over the service's lifetime.
  • Process objects are never disposed.

Not on GitHub; it was never under version control. Happy to walk through the source. The drawing is a reenactment with a generic Play button, no game art.

Distributed MapReduce

Blip builds it.

A manager/worker MapReduce framework over raw TCP and HTTP sockets.

A manager process partitions the input, hands map and reduce tasks to six worker processes, and coordinates the shuffle between them. Heartbeat monitoring catches workers that go silent, and their tasks are reassigned, so a job recovers within roughly one to two seconds under injected faults with no finished work lost.

  1. The manager splits the input into partitions.

    manager · TCP

  2. Map tasks run across six worker processes.

    6 workers

  3. Intermediate output is shuffled to the right reducers.

    shuffle

  4. Reduce tasks write the final output.

    reduce

  5. Heartbeats reveal a worker that went silent.

    heartbeat monitoring

  6. Its tasks are reassigned, and finished work is kept.

    recovers in ~1–2 s under injected faults

What I built

  • A Manager/Worker MapReduce framework over raw TCP and HTTP sockets that partitions input, coordinates the intermediate shuffle, and distributes map and reduce tasks across six worker processes.
  • Heartbeat monitoring and task reassignment, so the manager detects silent workers and restores full job progress within roughly one to two seconds under injected faults, with no loss of finished work.
